## 背景

0149 監査の所見 E1（entrypoints: `cmd/runner`・`cmd/record`・`cmd/verify`・`bootstrap`）のうち、Task 0150〜0161 のいずれの対象にもならず未着手のまま残っている Medium 3件（M-1・M-2・M-3）をまとめて解消する。3件はいずれも `runner`・`verify` の起動処理という同一領域に属する。

### M-1: `--run-id` が未検証のままログファイル名・ログ行に埋め込まれる

`runner` の `--run-id` フラグは「指定しなければ ULID を自動生成する」と説明されているが、ユーザー指定値に対する形式検証が一切行われず、以下2つの被害が成立する。

1. **ログディレクトリ外へのファイル作成・切り詰め**: run ID はログファイル名の一部として使われる。パス区切り文字や `..` を含む値を指定すると、`--log-dir` で指定した範囲の外にファイルを作成し、既存ファイルを切り詰められる。
2. **ログ行の偽装（ログ行注入）**: run ID は機械可読なサマリ行（`RUN_SUMMARY`）と標準エラー出力に埋め込まれる。空白・改行を含む値を指定すると、これらを解析する監視スクリプトに偽の行を読ませられる。

run ID はこの2つ以外にも Slack 通知や dry-run 出力へ流れる。本タスクは入口（フラグ解析直後）で不正値を遮断する方針を採り、下流の出力先はすべてこの入口検証によって保護されるものとする。

さらに、**不正値を拒否する経路自体が同じ被害を再現しうる**点に注意が必要である。現行の起動前エラー報告は、渡された run ID を `RUN_SUMMARY` 行と標準エラー出力にそのまま埋め込む。ここに未検証のユーザー入力を渡すと、拒否した瞬間にログ行注入が成立する。

`--run-id` を持つのは `runner` のみで、`record`・`verify` にこのフラグは存在しない。自動生成される値は ULID（Crockford Base32・26文字）であり、これが「正規の run ID」の基準となる。

### M-2: 起動時特権降格が実効ユーザーIDのみ（実効グループID未降格、実行順序も不適切）

`runner` は setuid-root バイナリとしての起動を前提とし、起動直後に実効ユーザーIDを実ユーザーIDへ降格している。しかし以下2点が未対応。

1. 実効グループIDが降格されず、特権グループのまま残る。バイナリが setgid 構成で配布・インストールされた場合、以後の全処理（フラグ処理、ログ設定、設定読み込み、権限チェック、コマンド実行準備）が特権グループのまま走る。現行の setuid-root のみの配布構成では実害はないが、この防御は配布構成に暗黙のうちに依存しており、構成が変わると前提が崩れる。
2. 降格処理がコマンドライン引数の解析より後に実行されている。「特権降格は可能な限り早く」という原則からの逸脱であり、引数解析自体が攻撃対象領域を広げるわけではないが、原則としての一貫性を欠く。

0157/0160/0161 で整理された「子コマンド実行時の特権指定への一本化」は、実行する**子コマンドへの** per-command 特権付与を扱うものであり、`runner` バイナリ**自身**が起動直後に行う自己降格（本件）とは別レイヤーであるため、これらのタスクによって本件は解消されていない。

### M-3: verify の TOCTOU チェックが fail-open（警告のみで続行）

TOCTOU（Time-Of-Check-To-Time-Of-Use。チェック時点と使用時点の間の状態変化を突く競合状態）を防ぐため、`verify` は対象ファイルとハッシュディレクトリの祖先ディレクトリ権限をチェックしている。しかし違反を検出しても警告として記録するだけで、検証処理をそのまま継続する。

対比として `record` は、ハッシュ DB を root of trust（信頼の起点）と位置づけ、同じ違反を検出した時点でハッシュ記録の生成を拒否する（fail-closed）。

`verify` は任意のハッシュディレクトリを指定できるため、攻撃者がそこへ書き込める状態（＝違反が検出されるケースそのもの）ではハッシュ記録を差し替えられる。ハッシュ記録が差し替え可能なら、対象ファイルを書き換えたうえで対応するハッシュ記録も書き換えれば検証は通る。この状態で `verify` が `OK`／exit 0 を返すと、それを信頼判断に使う運用者や監視スクリプトが改ざんを見逃す。

なお、**信頼できなくなるのはハッシュディレクトリ側の違反だけである**。対象ファイルが置かれたディレクトリが書き込み可能であることは、`verify` がまさに改ざんの有無を確かめるべき状況そのものであって、検証を拒否する理由にはならない。ハッシュ記録が保護されている限り、書き換えられたファイルは検証失敗として正しく報告される。この区別は fail-closed の適用範囲を決める（F-004 を参照）。

## 目的

- `--run-id` にユーザー指定の任意文字列を許さず、正規の形式のみを受理し、形式に反する値は起動前に拒否する。拒否経路自体が M-1 の被害を再現しないことを保証する。ログファイル名の構築側にも多層防御を設ける。
- `runner` の起動時特権降格を、実効グループIDを含めたうえで、いかなる入力処理よりも前に完了させる。
- `verify` の TOCTOU チェックのうち、ハッシュディレクトリとその祖先ディレクトリの違反を fail-closed（対象ファイルを1件も検証せず非ゼロ終了）とし、`record` との非対称を解消する。

## スコープ

### 対象

1. `runner` における `--run-id` の形式検証と、不正値の起動前拒否。拒否時の出力に不正値が漏れないことを含む。
2. run ID を用いたログファイル名構築における多層防御（入口検証を経ない経路でもログディレクトリ外にファイルを作らない）。
3. `runner` の起動時特権降格の完全化（実効グループIDを含む）と実行順序の是正。
4. `verify` の TOCTOU チェックのうち、ハッシュディレクトリとその祖先ディレクトリに関する違反の fail-closed 化。
5. 上記に対応するテストの追加・更新。
6. 影響を受ける利用者向け文書および CHANGELOG の更新。

### 対象外

- `record`・`verify` への `--run-id` フラグの新設（現状どちらにも存在せず、本タスクはその追加を含まない）。
- 補助グループ（supplementary groups）の降格。所見 M-2 の推奨対応は実効グループIDの降格のみを挙げており、補助グループの取り扱いは対象外とする（将来必要になった場合は別タスクとする）。
- run ID の下流の出力先（Slack 通知、dry-run 出力）における個別のエスケープ処理。入口検証で保護されるため追加対応は行わない。
- TOCTOU チェック処理そのものの挙動変更。同処理は `runner` を含む複数の呼び出し元で共有されているため、fail-closed 化は `verify` 側で行う。
- `record` の権限チェックの挙動変更（既に fail-closed であり、本タスクでは変更しない）。
- run ID 生成に用いる ULID ライブラリの差し替え。
- `runner` の native root 実行サポートの是非（[#921](https://github.com/isseis/go-safe-cmd-runner/issues/921)）。
- E1 の L-1〜L-7・I-1〜I-6（[#986](https://github.com/isseis/go-safe-cmd-runner/issues/986) で別途管理）。特に以下は本タスクと隣接するが対象外:
  - L-2（絶対パス化・シンボリックリンク解決の失敗時のサイレントフォールバック）
  - L-3（`verify` のハッシュディレクトリ作成副作用とパーミッション不一致）。この副作用は現行では TOCTOU チェックより前に発生するため、F-004 の fail-closed 化後もハッシュディレクトリの作成自体は起こりうる（AC-19 の注記を参照）。
  - I-1（起動時降格後も saved-uid が root のままである設計意図の文書化）

## 未決事項

以下は利用者から観測できる仕様であり、AC の確定に必要だが本書では決定しない。`02_architecture.md` で決定する。

- **`--run-id` の受理形式**: 厳密な ULID に限定するか、より緩い文字集合（英数字・アンダースコア・ハイフン）と長さ上限を許容するか。いずれの場合も許可リスト方式とし、ログディレクトリ外への書き込みとログ行注入を防げる文字集合であること。
- **`verify` の fail-closed 時の終了コード**: ハッシュ検証失敗（現行 exit 1）と「検証結果が信頼できない」を監視スクリプトが区別できるよう別の値を割り当てるか、`record` と同じ exit 1 に揃えるか。

## Acceptance Criteria

#### F-001: `--run-id` の形式検証

`runner` が `--run-id` に指定された値を検証し、不正な形式であれば起動前に拒否する。

**Acceptance Criteria**:
- **AC-01**: `--run-id` を指定しない場合、既存どおり ULID が自動生成され、実行が継続する（既存の起動テストが通過する）。
- **AC-02**: `--run-id=""`（明示的な空文字列）を指定した場合、未指定と同一に扱われ、ULID が自動生成されて実行が継続する（現行挙動の維持）。
- **AC-03**: 受理形式に合致する値を指定した場合、その値がそのまま run ID として採用され、実行が継続する。
- **AC-04**: 検証は許可リスト方式であり、受理形式に合致しない値はすべて拒否される。AC-05〜AC-07 はその代表例であって、拒否対象の網羅列挙ではない。
- **AC-05**: パス区切り文字や `..` を含む値を指定した場合、実行前に拒否され、非ゼロで終了する。
- **AC-06**: 空白・改行・その他の制御文字（NUL、ESC を含む）を含む値を指定した場合、実行前に拒否され、非ゼロで終了する。
- **AC-07**: 受理形式の長さ上限を超える値を指定した場合、実行前に拒否され、非ゼロで終了する。
- **AC-08**: AC-05〜AC-07 の拒否は起動前エラーとして扱われ、エラーの種別がプログラムから判別できる。この時点でログファイルは作成されない（`--log-dir` 配下にもそれ以外の場所にもファイルが作られない）。
- **AC-09**: AC-05〜AC-07 の拒否時、指定された不正値が標準出力・標準エラー出力・ログのいずれにも原文のまま出現しない。特に機械可読なサマリ行の `run_id` フィールドには、自動生成された正規の値が入る。
- **AC-10**: AC-05〜AC-07 の拒否時、標準エラー出力に受理される形式を示すメッセージが出力される。

#### F-002: ログファイル名構築側の多層防御

run ID を用いたログファイル名の構築が、run ID に起因するパストラバーサルを二重に防ぐ。

**Acceptance Criteria**:
- **AC-11**: 構築されるログファイルのパスが、指定されたログディレクトリ直下から外れる run ID を与えられた場合、ログファイルを作成せずエラーとなる。
- **AC-12**: AC-11 の防御は、F-001 の入口検証を経由しない呼び出し（テストからの直接呼び出し等）に対しても機能する。
- **AC-13**: 正規の形式の run ID を与えた場合、既存のログファイル作成テストが通過する。

#### F-003: 起動時特権降格の完全化と実行順序修正

`runner` の起動時特権降格が、実効グループIDを含めて、いかなる入力処理よりも前に完了する。

**Acceptance Criteria**:
- **AC-14**: 実効グループIDの降格が実効ユーザーIDの降格より先に行われ、両方ともコマンドライン引数の解析より前に完了する。この順序が検証できる。
- **AC-15**: 実効グループIDの降格に失敗した場合、実効ユーザーIDの降格は行われず、以降の処理も一切行わずに非ゼロで終了する（fail-closed）。
- **AC-16**: 実効ユーザーIDの降格に失敗した場合、AC-15 と同様に fail-closed となる（現行の挙動を維持）。
- **AC-17**: 降格処理を引数解析より前に移動した後も、既存のフラグ解析テストおよび起動テストが通過する。
- **AC-18**: AC-15・AC-16 の失敗時のエラー報告に含まれる run ID が、空文字列ではなく正規の形式である。

#### F-004: verify の TOCTOU チェック fail-closed 化

`verify` の TOCTOU 権限チェックで、ハッシュディレクトリまたはその祖先ディレクトリに違反が検出された場合、対象ファイルの検証を1件も行わず非ゼロで終了する。

**Acceptance Criteria**:
- **AC-19**: ハッシュディレクトリまたはその祖先ディレクトリに1件以上の違反が検出された場合、`verify` は対象ファイルを1件も検証せず、非ゼロで終了する。ここでの保証は検証処理の実行有無についてのものであり、引数解析時に発生するハッシュディレクトリ作成の副作用は含まない（L-3、対象外）。
- **AC-20**: AC-19 の場合、fail-closed の判定対象となった各違反がエラーレベルで記録される。これは共有の TOCTOU チェック処理が出力する警告レベルのログに**加えて**行われる（`record` と同じ扱い）。
- **AC-21**: AC-19 の場合、標準エラー出力に「検証結果は信頼できない」旨と是正方法（該当ディレクトリの権限修正）を示すメッセージが出力される。
- **AC-22**: ハッシュディレクトリ側に違反が検出されない場合、既存どおり検証が継続され、終了コードはファイルごとの検証結果のみに依存する（既存の `verify` テストが通過する）。
- **AC-23**: AC-19 の fail-closed 判定が、既定のハッシュディレクトリを使用する場合と、コマンドラインでハッシュディレクトリを明示した場合の両方で機能する。
- **AC-28**: 対象ファイルの祖先ディレクトリのみに違反が検出され、ハッシュディレクトリ側には違反がない場合、`verify` は fail-closed とならず検証を継続する。この違反は従来どおり警告として記録される。対象ファイルが書き込み可能なディレクトリに置かれていることは、`verify` が検出すべき状況そのものであって、検証を拒否する理由にはならない。

#### F-005: 文書の更新

本タスクによる利用者向けの挙動変化を文書に反映する。

**Acceptance Criteria**:
- **AC-24**: `runner` の利用者向け文書に、`--run-id` が受理する形式と、不正な値を指定した場合に起動前に拒否されることが記載されている。日本語版を先に更新し、英語版は `/mktrans` で反映する。
- **AC-25**: `verify` の利用者向け文書に、ハッシュディレクトリまたはその祖先ディレクトリに違反が検出された場合は対象ファイルを1件も検証せずに非ゼロで終了すること、および対象ファイル側のみの違反では警告のうえ検証が継続することが記載されている。日本語版を先に更新し、英語版は `/mktrans` で反映する。
- **AC-26**: `CHANGELOG.ja.md`／`CHANGELOG.md` に破壊的変更として2点（`--run-id` の形式厳格化、`verify` のハッシュディレクトリ違反に対する fail-closed 化）が記載されている。既存の CI・運用スクリプトが影響を受け得るため、影響範囲と対処が読み取れる記述であること。
- **AC-27**: `docs/translation_glossary.md` に、本タスクで新たに導入した用語があれば追加されている。

## Success Criteria（要件レベル）

- 上記すべての Acceptance Criteria が実装され、対応するテストが `make test` で成功する。
- `make lint` が警告なく通過する。
- `runner` について、受理形式に合致する `--run-id` を指定する通常運用、および `--run-id` を指定しない通常運用のいずれにおいても、0149 完了時点からの外部から観測可能な挙動の変化がない。
- `verify` について、ハッシュディレクトリ側に違反が検出されない通常運用では、0149 完了時点からの外部から観測可能な挙動の変化がない。これには `sudo verify` で利用者のホームディレクトリ配下のファイルを検証する運用を含む。
